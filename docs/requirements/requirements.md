# 要件定義書：Redmine連携 PM向け日次レポート

## 1. 概要
Redmineの指定プロジェクト1件（サブプロジェクトを含む）について、日々のチケット活動（新規登録・
ステータス／担当者の変更）、作業時間（Spent time）、遅延・期限超過チケットを集計し、PM向けの日次レポートを
自動生成する仕組みを構築する。Windowsのタスクスケジューラが平日（月〜金）に定期的に起動するバッチ処理が
Redmine REST APIから情報を取得してレポートを生成し、PMはWeb画面でレポート一覧・詳細・バッチの実行履歴を
閲覧したうえで、単日または期間を指定してMarkdownファイルとしてエクスポートできる。

本プロジェクトは、既存の
[Lychee-redmine-loop-engineering-](https://github.com/theta1211/Lychee-redmine-loop-engineering-)
（Redmineチケットを自動実装するループエンジン）の構成・設計方針
（npm workspacesによるモノレポ構成、DBを使わずJSONファイルで状態管理、Windowsタスクスケジューラでの定期実行、
IIS＋iisnodeによるWindows統合認証・Web画面公開）を踏襲する。

## 2. 登場する要素
| 要素 | 役割 |
|---|---|
| レポート生成バッチ | タスクスケジューラから起動され、対象日の活動をRedmine REST APIから収集し、レポートを生成・保存する |
| Web画面（レポート閲覧アプリ） | 生成済みレポートの一覧・詳細・Markdownエクスポート・バッチ実行履歴の確認・手動再生成を提供する |
| Redmine（既存システム） | チケット・作業時間・更新履歴の取得元。新規構築はせず既存サーバーを利用する |
| 対象Redmineプロジェクト | レポート対象。当面は1プロジェクト（サブプロジェクト含む）に固定（設定ファイルで指定） |
| Windowsタスクスケジューラ | レポート生成バッチを平日（月〜金）1日1回起動するトリガー |
| PM（利用者） | Windows統合認証で識別。Web画面でレポートを閲覧・エクスポートし、必要に応じて手動再生成する |

## 3. 全体構成図
```
[Windowsタスクスケジューラ] ──平日(月〜金)の決まった時刻に起動──▶ [レポート生成バッチ]
                                                                        │
                                                                        ▼
                                                               [Redmine API]
                                                               ・チケット一覧/更新履歴(journals)
                                                               ・作業時間(time_entries)
                                                               ・予定工数(Estimated hours)/進捗率(Done ratio)
                                                                        │
                                                                        ▼
                                              [レポートデータ／実行履歴(JSONファイル)] 対象日ごとに保存
                                                                        ▲
                                                                        │ 一覧取得・詳細取得・手動再生成の指示
[PM] ──Windows認証でログイン──▶ [Web画面(レポート閲覧アプリ)]
                                          │
                                          ▼
                                Markdownファイルとしてエクスポート（単日／期間指定）
```
※ レポート対象日は「起動日の直前の営業日（月〜金）」とする。タスクスケジューラも平日のみ起動するため、
　月曜日に起動するバッチは前週金曜日分のレポートを生成する。

## 4. 機能要件

### 4.1 レポート生成バッチ

#### 起動・対象日
- Windowsタスクスケジューラにより、平日（月〜金）1日1回、設定した時刻に起動される（土日は起動しない）。
- 対象日は「起動日の直前の営業日（月〜金）の0:00〜23:59、JST基準」とする。
  起動日から1日ずつ遡り、最初に見つかった平日を対象日とする（月曜日に起動した場合は前週金曜日が対象日となる）。
  祝日は考慮しない。
- 集計対象トラッカーは設定ファイルでトラッカー名の配列として指定する（例: `["タスク", "バグ"]`）。
  以降の新規登録・更新・作業時間集計・遅延判定はすべてこの対象トラッカーに限定する。
- 対象プロジェクトのサブプロジェクトも含めて集計し、プロジェクト単位で分けず全体を合算した1つのレポートに
  まとめる。

#### 取得・集計する情報
Redmine REST APIから以下を取得し、対象日単位で集計する。

1. **新規登録チケット**：対象日に起票されたチケットを、チケット番号・件名・起票者・トラッカー・優先度・
   担当者（未アサインの場合は「未アサイン」）・期日（Due date）とともに一覧化する。
2. **更新チケット**：対象日にステータスまたは担当者が変更されたチケットを対象とする（journalsベース）。
   同一チケットが対象日中に複数回変更されても集計・件数カウントは1件とし、表示にはその日の変更点
   （例：「ステータス：新規 → 進行中」「担当者：山田 → 佐藤」）をまとめて記載する。
3. **作業時間（Spent time）集計**：対象日を作業日（`spent_on`）とする作業時間を、工数を入力した利用者
   （Redmineの`time_entry.user`。チケットの担当者とは別）ごとに合計する
   （表示単位は時間、小数点1桁。例：7.5h）。チケット別の内訳は持たない。
4. **遅延・期限超過チケット**：対象日（直前の営業日）時点の状態を基準に、期日（Due date）が対象日より前で、
   かつステータスが完了（Redmineのステータス`is_closed`属性が真）でないチケットを遅延チケットとする。
   - 遅延時間（h）= 予定工数（Estimated hours）×（1 − 進捗率（Done ratio）／100）
   - 予定工数（Estimated hours）が未設定のチケットは遅延時間を計算せず、「計算不可（工数未設定）」として
     一覧の末尾に別掲する。
   - 担当者未設定のチケットも対象に含め、担当者欄は「未アサイン」と表示する。
   - 一覧は遅延時間（計算値）の降順で表示する（計算不可のものは末尾にまとめる）。

#### サマリ
- 新規登録件数、更新件数（チケット単位）、作業時間合計（入力者別合計の総和）、遅延件数
  （総数と、そのうち「計算不可」の件数）をサマリとして作成する。

#### 保存・異常系
- 生成したレポートデータをJSONファイルとして`data/`配下に、対象日単位で1ファイル保存する。
- 同一対象日のレポートが既に存在する場合は再生成し上書きする（多重登録は行わない）。
- Redmineへの接続失敗や取得中のエラーが発生した場合、自動リトライは行わず、レポートを「生成失敗」として
  記録する（要因が分かるメッセージのみを記録する。例：「Redmineへの接続に失敗しました」）。生成失敗は
  次回のスケジュール起動に影響を与えない。
- すべてのバッチ実行（自動・手動を問わない）について、対象日・実行時刻・成功／失敗を実行履歴として
  記録し、レポートデータとは別に保存する。
- レポート生成バッチが多重起動しないよう排他制御を行う。

### 4.2 Web画面（レポート閲覧アプリ）
- Windows統合認証でログインユーザーを識別する（IIS＋iisnode構成。Loop engineeringと同様）。
  非Windowsの開発・検証環境向けに、環境変数でログインユーザーを指定できる代替手段を用意する
  （Loop engineeringの`DEVLOOP_DEV_USER`相当）。
- 生成済みレポートを日付の一覧として表示する（新しい日付から順）。生成失敗のステータスも表示する。
- 一覧から任意の日付を選び、レポート詳細（新規登録・更新・作業時間集計・遅延チケット・サマリ）を
  画面上で確認できる。
- 表示中のレポートをMarkdownファイルとしてエクスポート（ダウンロード）できる（単日単位）。
- 開始日・終了日を指定し、期間内の複数日分をまとめて1つのMarkdownファイルとしてエクスポートできる。
  - 指定できる期間は最大31日とする。
  - ファイルの冒頭に期間全体のサマリ（合計作業時間・新規件数合計・期間内で最も新しい対象日時点の
    遅延件数など）を記載し、続けて日ごとの詳細を記載する。
- ログインしたPMは誰でも、任意の対象日を指定してレポートを手動で再生成できる（自動生成の失敗や
  欠測日のリカバリ用）。保持期間（後述）を超えた過去日を指定した場合も生成自体は許可するが、
  次回の保持期間クリーンアップ処理で速やかに削除対象となる。
- 手動再生成の実行中は操作したPMの画面でボタンをローディング表示にし、完了後に結果（成功・失敗）を
  画面へ反映する。他の利用者の画面に「実行中」を表示する仕組みは設けず、重複実行は排他制御で弾く。
- バッチの実行履歴（自動・手動を問わず、対象日・実行時刻・成功／失敗）を一覧で確認できる。

### 4.3 Redmine連携
- 既存のRedmineサーバーを利用する（URL・APIキーを`config.json`（`.gitignore`対象）に設定情報として
  保持する。雛形として`config.example.json`を用意する）。
- チケット一覧・更新履歴（journals）・作業時間（time_entries）・予定工数／進捗率の取得に対応する。
- チケットのステータス変更・完了操作は本仕組みでは行わない（参照のみ）。

## 5. 非機能要件
- Web画面はLAN内にHTTPで公開する（HTTPS化は行わない。Loop engineeringと同様）。
- Windows統合認証によりアクセス制御・利用者識別を行う。IISが認証したアカウント名をアプリへ渡す際は、
  クライアントが自称した同名のHTTPヘッダーを必ず上書きし、ヘッダー偽装による成りすましを防止する。
- Redmine APIキー等の認証情報は平文コミットせず、`config.json`（`.gitignore`対象）で安全に管理する。
- レポート生成バッチの異常終了が後続の定期実行に影響しないこと。
- レポート生成バッチの多重起動防止（排他制御）を行うこと。
- 生成済みレポートおよびバッチ実行履歴の保持期間は設定ファイルで変更可能とし、初期値は90日とする。
  保持期間はレポートの**対象日**を基準にカウントし、対象日が90日以上前になったものは自動削除する。
- DBは使用せず、JSONファイルで状態・レポートデータ・実行履歴を管理する（Loop engineeringと同様の方針）。
- タイムゾーンは日本時間（JST）固定とする。

## 6. 制約事項
- Redmine APIの利用制限（レートリミット等）に従う。
- 対象プロジェクトは1件（サブプロジェクト含む）固定とし、切り替えは設定ファイルの変更・再起動を要する。
- レポート生成は平日1日1回を基本とし、欠測日・失敗分の補完は手動再生成でのみ行う。
- 土日は対象日にならないため、土日に行われた活動はレポートの集計対象外となる。
- 祝日は考慮しないため、連休明けの自動生成では「直前の平日＝祝日」が対象日となり、活動なしのレポートが
  生成される。連休前の営業日分のレポートが必要な場合は、手動再生成で補完する。
- 作業時間は作業日（`spent_on`）基準で集計するため、レポート生成後に当該日の工数が追加入力された場合、
  生成済みのレポートには反映されない。最新化が必要な場合は手動再生成を行う。
- 「遅延時間」は予定工数と進捗率から算出する残作業量であり、期日からの超過日数とは連動しない
  （未着手で工数の大きいチケットが、長期間超過している小規模チケットより上位に並ぶことがある）。
- レポートの内容は「チケットの新規登録」「ステータス・担当者の変更」「作業時間集計」
  「遅延・期限超過チケットの検出（予定工数と進捗率に基づく遅延時間の算出を含む）」に限る
  （チケットコメント本文の要約は対象外）。
- 完全無人で日次生成させるため、タスクスケジューラの実行ユーザーがRedmine APIへ到達可能な
  ネットワーク環境にあることを前提とする。
- 遅延時間の算出は予定工数（Estimated hours）と進捗率（Done ratio）が入力されていることを前提とする
  （未入力の場合は計算不可として別掲するのみで、代替値による補完は行わない）。

## 7. スコープ外
- 複数Redmineプロジェクトの同時対応（当面は1プロジェクト固定。サブプロジェクトは対象に含む）。
- メール・Slack・Teams等、Web画面以外へのレポート配信・通知。
- チケットコメント（Notes）本文のAIによる要約。
- レポート内容に基づくチケットの自動操作（ステータス変更、リマインド送信等）。
- Redmine以外の課題管理ツールとの連携。
- 利用者ごとの個別権限設定（閲覧・手動再生成はログインしたPM全員が共通で可能とする）。
- バッチ失敗時の自動リトライ、および画面上でのエラー詳細（スタックトレース等）表示。
- 祝日カレンダーに基づく対象日の制御。
- 生成済みレポートの自動追い直し（後から入力された工数の自動反映）。
